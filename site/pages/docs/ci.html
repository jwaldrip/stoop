The shape of it

Every recipe has the same three parts:

  1. Install stoop on a Linux runner.
  2. Wrap the steps. In GitHub Actions one defaults block does it; elsewhere, put stoop run -- in front of each command.
  3. Share proofs between runs. A fresh runner has an empty .stoop/, so nothing would ever skip. Either cache that directory with the CI's own cache, or sync proofs through your git remote. Pull request runs read; only the default branch writes.

Why only the default branch writes. A proof is a claim that lets later runs skip checks. Proofs written by code that hasn't been reviewed shouldn't let main skip anything. Branches read main's proofs, so a branch that matches main skips what main already proved.

Prebuilt binaries support Linux x86-64 and arm64, and macOS x86-64 and arm64. macOS runs commands untraced and records nothing. To see what a command does on a GitHub-hosted macOS runner, set STOOP_DTRACE_DIAGNOSTIC=1: stoop runs the command once under DTrace and prints what it looked at. That output is a diagnostic. It is never recorded, so nothing is skipped. Blind spots says why.

GitHub Actions

With sync through the repository's own remote. Proofs live at refs/stoop/<key>, which branch and tag listings ignore.

name: CI
on:
  pull_request:
  push:
    branches: [main]

defaults:
  run:
    shell: stoop sh {0}       # every run: step goes through stoop

jobs:
  test:
    runs-on: ubuntu-latest
    permissions:
      contents: write          # main pushes refs/stoop/*
      id-token: write          # attests the records this job publishes
    env:
      STOOP_SYNC: git
    steps:
      - uses: actions/checkout@v4
      - name: Install stoop
        shell: bash               # stoop is not installed yet
        run: |
          curl -fsSL https://stoop.build/install.sh | sh
          echo "$HOME/.local/bin" >> "$GITHUB_PATH"
      - name: Publish proofs from main only
        if: github.ref == 'refs/heads/main'
        shell: bash
        run: echo "STOOP_SYNC_WRITE=1" >> "$GITHUB_ENV"
      - name: Fetch published proofs
        shell: bash
        run: stoop pull
      - run: cargo fmt --check
      - run: cargo clippy --all-targets -- -D warnings
      - run: cargo test
  • Each wrapped step is keyed by its script, the workflow and the job, so the same script in two jobs gets two keys.
  • Steps that use an action (uses:) are not shell steps and run as usual.
  • Set STOOP_SYNC_WRITE only on the default branch. An empty value or 0 is off, so STOOP_SYNC_WRITE: ${{ github.ref == 'refs/heads/main' && '1' || '' }} works; setting it from a step guarded by if:, as above, is just as good.
  • Sync never fails a step. If the remote is unreachable or refuses a push, stoop warns and the step runs as it would have without sync.
  • Publishing jobs can attach a GitHub OIDC token to each record with id-token: write. The experimental planner refuses records without a valid token. Planning needs contents: read, access to token.actions.githubusercontent.com, the sync remote, git ls-remote access to GITHUB_SERVER_URL, and access to the GitHub archive API. Action downloads use the checkout's Git HTTP credentials when available. The runner's proxy and certificate environment is part of the trust base.
  • Tokens identify the workflow and run, not an individual job. Any process with the request credentials can request a token for records of another job in that workflow; a separate writer can publish it later. The signed issue time limits its usable age to the planner's ceiling. Restrict publishing permissions and use an ephemeral GitHub-hosted planner runner.
  • The planner accepts only protected branches and GitHub-hosted recording runners. The planned workflow file must be the same file that recorded the job. A separate main-only workflow with the same name cannot supply its records. GitHub Enterprise Server and GitHub Enterprise Cloud custom OIDC issuers are not supported and fail closed.

Stoop captures ACTIONS_ID_TOKEN_REQUEST_URL and ACTIONS_ID_TOKEN_REQUEST_TOKEN for its own attestation requests and removes them before starting commands, probes, or helpers such as Git hooks. This prevents accidental inheritance, not deliberate access: on Linux, same-user processes may read the original environment from /proc/<pid>/environ, and the runner or other steps can still hold the credentials. A command that needs them must list each name in STOOP_PASS_ENV and pass --allow-id-token, for example by setting the step's environment and using shell: stoop sh --allow-id-token {0}. That command runs untraced, without using or writing a proof, and blocks job attestation; it joins the workflow's token trust base.

Experimental job planning

Do not enable plan-skips in workflow gates yet. Planning remains experimental until its integration and required gates are verified. STOOP_STRICT_ACTIONS=1 additionally refuses floating remote action refs.

The plan job must live in the top-level workflow. Set STOOP_JOB_WORKFLOW_REF: ${{ job.workflow_ref }} on the plan step. A missing or different value makes every job run. Image ENV and neutral setup must not set STOOP_* controls; the planner assumes this and does not verify it. Nonempty container options are not plannable.

Set STOOP_ALLOW_USES at workflow or job level to exact comma- or newline-separated owner/repo or owner/repo@ref entries. This is the workflow author's assertion that those actions are side-effect free. --allow-uses is for local dry runs only. The plan job and publishing jobs need the same STOOP_ENV_SALT when proofs are salted.

A proved leg's JSON record includes a digest of the job record and its ordered step proof digests. These identify the evidence used; they do not preserve records after retention or pruning removes them. Run decisions have no record.

When a proof recorded a git blob id for a repository file, the planner compares that id with the file's blob at the planned revision and does not read the file. Equal ids mean the step would read the same bytes. The shortcut applies only when no conversion attribute or core.autocrlf applies to the file, the repository uses SHA-1 object ids, and the recorded id is well formed. Every other comparison hashes the file, as before. stoop plan --prefilter on is the default, off hashes every file, and check evaluates each record both ways and fails the job on any difference.

A proved leg's checked object counts its comparisons. by_oid counts those decided by blob id, hashed counts those that read or hashed the file, blob_reads counts the blob reads the record needed, and declined counts the comparisons that fell back, by reason. The reasons are oid-unavailable (no blob id was recorded, for example a proof recorded before blob ids or a directory alias), conversion (a conversion applied when the proof was recorded), object-format (the repository or the recorded id is not SHA-1), mode (the executable bit differs from the tree), and id-malformed (the content id is not a valid hash). --explain prints each comparison that used a blob id and each reason it did not.

Or with the Actions cache

If you'd rather not give the job push access, cache .stoop/. A run can restore caches saved on its own branch and on the default branch (GitHub's cache access rules), so save only on main:

      - uses: actions/cache/restore@v4
        with:
          path: .stoop
          key: stoop-${{ github.job }}-${{ github.run_id }}
          restore-keys: stoop-${{ github.job }}-
      # ... your run: steps ...
      - if: github.ref == 'refs/heads/main'
        uses: actions/cache/save@v4
        with:
          path: .stoop
          key: stoop-${{ github.job }}-${{ github.run_id }}

GitLab CI

GitLab keeps caches for protected and unprotected branches separate by default (GitLab caching docs), so a merge request pipeline can't read the cache main saved. Git sync is the way to share main's proofs with merge requests:

test:
  image: rust:1
  variables:
    STOOP_SYNC: git
  before_script:
    - curl -fsSL https://stoop.build/install.sh | sh
    - export PATH="$HOME/.local/bin:$PATH"
    - if [ "$CI_COMMIT_BRANCH" = "$CI_DEFAULT_BRANCH" ]; then export STOOP_SYNC_WRITE=1; fi
    - stoop pull
  script:
    - stoop run -- cargo test

Reading uses whatever credentials the checkout used. Publishing from main needs a token allowed to push to the repository; point a remote at it and name that remote in the spec, for example STOOP_SYNC: git:publish.

The simpler, per-branch alternative: cache .stoop/ with key: stoop-$CI_JOB_NAME-$CI_COMMIT_REF_SLUG. Each branch then reuses its own earlier pipelines' proofs, but starts cold.

CircleCI

Restore everywhere, save from main only, using a step-level when:

version: 2.1
jobs:
  test:
    docker:
      - image: rust:1
    steps:
      - checkout
      - run: curl -fsSL https://stoop.build/install.sh | sh && echo 'export PATH="$HOME/.local/bin:$PATH"' >> "$BASH_ENV"
      - restore_cache:
          keys:
            - stoop-main-
      - run: stoop run -- cargo test
      - when:
          condition:
            equal: [ main, << pipeline.git.branch >> ]
          steps:
            - save_cache:
                key: stoop-main-{{ .Revision }}
                paths: [ .stoop ]

Or use git sync exactly as in the GitLab recipe, gating STOOP_SYNC_WRITE on CIRCLE_BRANCH.

Buildkite

Buildkite has no built-in cache on self-hosted agents, which makes git sync the natural fit: nothing to host, and the agent already talks to the remote.

steps:
  - label: ":rust: test"
    env:
      STOOP_SYNC: git
    command: |
      if [ "$BUILDKITE_BRANCH" = "$BUILDKITE_PIPELINE_DEFAULT_BRANCH" ]; then export STOOP_SYNC_WRITE=1; fi
      stoop pull
      stoop run -- cargo test

Install stoop on the agent image once. Publishing needs the agent's git credentials to allow pushes from default-branch builds.

How git sync works

  • --sync git (or STOOP_SYNC=git) uses the remote named origin; git:NAME picks another.
  • On a miss, stoop fetches refs/stoop/<key> for that one key and checks again. stoop pull fetches every published proof once, which is cheaper at the start of a job that runs many steps.
  • The planner lists refs/stoop/* once, then fetches records for planned jobs and proofs named by eligible, matching records. If sync takes more than 60 seconds, the listing exceeds 100,000 refs or 16 MiB, a ref exceeds 64 MiB, or fetched refs exceed 512 MiB in total, every job runs. The byte limits apply to the listing and declared blob sizes, not to Git's network download.
  • With --sync-write (or STOOP_SYNC_WRITE=1), a recorded run publishes its proofs, merged with what is already there.
  • stoop prune deletes published proofs older than --max-age (default 7 days). It needs write access; a scheduled job on main is the place for it.
  • Shallow checkouts are fine: the proof refs are fetched on their own.
  • Proofs record a hash of every environment variable, and published proofs are readable by anyone who can read the repository. An unsalted hash of a low-entropy value (a short token, a flag) can be guessed offline. Set STOOP_ENV_SALT from a repository secret on every job that records or checks proofs: the hashes are then keyed with it (they start with s:) and stoop warns when it publishes without one. A run without the secret, such as a pull request from a fork, cannot match a salted proof and simply runs the command. Proofs published before you set it keep their unsalted hashes until they expire or you remove them with stoop prune --max-age 0.

In GitHub Actions, stoop sh keeps a job journal in RUNNER_TEMP. Trusted sync writers publish job records alongside step proofs. The planner verifies the record's attestation, step proofs, and action-content witness before allowing a skip. Keep write credentials unavailable to pull requests.

At the first recorded stoop sh step, stoop resolves each action ref, downloads the repository archive at that commit, and hashes the files and executable bits. It compares that tree with the runner's downloaded _actions copy, then follows composite actions' nested uses: refs. Local actions are compared with their committed tree. Docker actions need an image pinned by a SHA-256 digest. A missing copy, corrupt or incomplete archive, unavailable repository, unsupported archive entry, oversized download, or timeout leaves the job without a usable action witness.

Archive downloads follow at most three redirects and remain on the original URL scheme. Curl does not forward the checkout authorization header to a different host.

The planner resolves refs again and downloads fresh archives for the planned run. A moved ref reports action-moved, changed archive contents report action-content-changed, and an unavailable or unsupported check reports action-unverifiable. All three run the job. A process-local cache avoids duplicate downloads during one plan, with a 512 MiB total retained-tree budget across jobs. Actions exceeding the budget make their jobs run. Action archives are not written to disk. Reusable-workflow jobs remain unplannable because their records cannot satisfy the current attestation policy.

Archive and runner-copy comparison covers committed files, including committed node_modules. It does not continuously monitor the action directory or verify dependencies installed or changed after the snapshot. The runner's preinstalled tools, tool cache, preinstalled actions, and toolchains downloaded by actions remain outside this check. See action and tool limits.

Container and service images must be pinned to digests or the job runs. Optional STOOP_STRICT_ACTIONS=1 rejects floating remote action refs at recording and planning; it is off by default.

Tested: the sync suite runs against a bare git remote, and the ref mechanics (push, shallow fetch, delete) were checked against GitHub. Not yet verified: a full authenticated sync run inside a hosted CI provider.

The nightly full run

A file trace can't see the clock. Re-prove everything on a schedule so a test that depends on today's date can't hide behind a proof for long:

on:
  schedule:
    - cron: "17 4 * * *"
env:
  STOOP_FULL: "1"            # never skip, still record
