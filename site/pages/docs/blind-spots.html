The network

A response from a server never shows up as a file read. So a run that connects out is not recorded, and stoop says where it connected:

stoop: not recorded: it used the network (connect to 192.168.64.1:53), whose results a file trace cannot see; cover it with --probe, or pass --allow-network to record it anyway

Connections to local services (a database on a Unix socket or localhost) are treated the same way. You have two ways to cover it:

--probe CMD

Tell stoop how to check the external thing. The probe's output is hashed into the proof and must match before a skip. It runs before the command and again after, and if it changed in between, nothing is recorded.

$ stoop run --probe 'curl -s https://example.com | sha256sum' \
    -- sh -c 'curl -s https://example.com > page.html'
stoop: run sh-c98f8f9c8fef6d65: no proof yet
stoop: recorded 71 inputs for sh-c98f8f9c8fef6d65
$ stoop run --probe 'curl -s https://example.com | sha256sum' \
    -- sh -c 'curl -s https://example.com > page.html'
stoop: skip sh-c98f8f9c8fef6d65: 71 inputs unchanged since 0s ago (100ms)

Good probes are cheap and exact: a lockfile hash from a registry, git ls-remote for a dependency's branch, a schema version from a migration table.

--allow-network
Record it anyway. You are saying the network can't change the result, for example a download whose content is already pinned by a checksum the command verifies.

The clock and randomness

A test that depends on today's date, or on a random seed, reads nothing that a trace can see. Two settings bound how long that can hide:

  • Expiry. A proof stops counting after 7 days by default. --max-age changes that; shorter is safer.
  • The nightly full run. STOOP_FULL=1 never skips and still records, so a scheduled run re-proves everything. See the recipe.

Flaky tests stay flaky. If one passes once, stoop records that pass. The determinism check on the roadmap is aimed at this.

Services outside the process tree

If a command depends on something it doesn't open itself, such as a daemon that reads files on its behalf, those reads are invisible. Cover the daemon's state with a probe, or don't wrap that step.

Output outside the repository

stoop checks that what a run wrote inside the repository is still there. It doesn't track output written elsewhere. A step whose whole job is to produce files outside the repository (publishing, deploying, filling a shared cache) shouldn't be wrapped.

Removed paths are listed in the proof for planning. A runtime skip does not check that those paths remain absent, so a command whose result depends on keeping a removed file absent needs another check or should run without skipping.

Reading .git

A command that reads .git could depend on history, which a working-tree comparison can't see. Such runs aren't recorded. If the read can't change the result, add .git to .stoopignore.

Writes through links

A write through a symbolic link changes its target and makes the proof unplannable. Stoop can also decline to record a run when it cannot establish where a write landed. Avoid retargeting links while a command runs.

Metadata

Only a file's bytes and its executable bit are compared. Modification times, owners and the other permission bits are not, so a tool that decides by timestamp is outside what a proof can show. A hard link to a repository file is not detected: a write through the link changes the file without the proof naming it.

Names that are not UTF-8

A run that accesses a repository path whose name is not valid UTF-8 is not recorded. This prevents a later skip from relying on a path the proof cannot represent faithfully.

Inherited input

A file opened before stoop starts and passed as standard input, or read through a bind mount alias that stoop cannot map to the repository, may not appear in the trace. If the command reads that file without writing it, changes may not prevent a runtime skip or a planned skip. For a file the run writes, the prior content is recorded.

Actions and runner tools

Job records compare each downloaded action repository tree with the runner's action copy when the journal opens. Composite actions' nested refs are checked too. A later plan resolves the refs and downloads the trees again. Unsupported entries, missing copies, unresolved refs, and changed contents make the job run.

The comparison is a snapshot, not continuous monitoring. Files changed while an action executes or after the journal opens are outside it. Committed node_modules are included in the tree; packages installed or modified at runtime are not. The runner's own tool cache, preinstalled actions, system software, and tools downloaded by setup actions can change without changing the action tree. Use pinned tool versions, probes, expiration, and full runs to bound those changes.

Planning assumes the runner would fetch the same GitHub API archive for the resolved commit. Stoop does not inspect a future runner copy, so an action served from a package with different runtime content would not be detected by this check. A digest-pinned docker:// image is identified by its digest; stoop does not inspect the image bytes.

Reusable-workflow jobs remain unplannable. Docker action tags, submodules, Git LFS pointers, symlinks, and unsupported archive entries fail wide rather than supplying an action witness.

Blob ids in planned skips

A recorded blob id stands for the bytes the step read. The planner relies on the recorder taking the blob id and the content id from one read of the file. A recorder that broke that pairing could let a planned skip where hashing would run, and the planner would not notice on its own. stoop plan --prefilter check compares both ways for every record it evaluates, so a disagreement fails the job.

Equal blob ids rest on git's object ids. Git's collision detection refuses objects that carry known SHA-1 collision attacks, and no second-preimage attack on SHA-1 is known. The planner does not check the runner's own configuration for conversions (for example core.autocrlf in the runner's global config); it relies on the runner identity, as hashing does.

A symbolic link needs no blob id. Its blob is its target text, and checkout does not convert links, so the planner derives the id from the recorded target. A target the recorder decoded lossily is read from the repository instead.

Recording drops a run's blob ids in the cases described in how it works. The planner then hashes the affected files, so these cost skips and never correctness. Three cases matter most. An untracked input has no committed blob, so it never carries an id. A step that writes the index, such as one that runs git add or git commit before the command, drops the ids of its run. A global configuration or attributes file that is a symbolic link, as dotfile managers often make it, declines every blob id in every run. Git must also report its global and attribute sources in git var -l; a Git that does not declines every blob id.

The changed-unit placeholder

Writing '{changed}' is a declaration. It says each test file passes alone exactly as it does in the full suite, and that running the command with no test files does nothing beyond running them all. stoop cannot see either premise. A test that depends on another test's side effect, shared state or a fixture built by an earlier test still looks independent on disk.

In this release a placeholder never runs a subset. It runs the full command with the placeholder and its option removed, and a run that executes the command prints the words it removed. That keeps the premise from changing any result yet. The rule stoop does enforce is that a shell-expanded form of a recorded placeholder runs the full command and never skips, so an unquoted or emptied placeholder cannot quietly match an older proof.

Cover the premise in your own CI by running the full suite with STOOP_FULL=1, and keep any suite whose tests depend on order out of a placeholder command, so the premise never applies to it. Quote every placeholder. The quoting table is in the CLI reference.

Variables that change on every run

The environment counts as an input, so a variable that changes on every run would make every proof miss. stoop leaves out two kinds of variable. A curated list covers the ones a shell, a terminal, a login session or a CI provider documents as per run, per session or per commit, and each name is listed with the page it was read from. A group that names one provider is ignored only where that provider sets its marker variable. Jenkins per-build names need JENKINS_HOME, which Jenkins sets for every build of a job, or JENKINS_URL, which it sets only when a root URL is configured, or TEAMCITY_VERSION. Jenkins executor and commit names need JENKINS_HOME or JENKINS_URL. The TeamCity commit prefix needs TEAMCITY_VERSION, Azure Pipelines names need TF_BUILD, and WINDOW needs STY, which GNU screen sets inside a session. Learning covers the rest. The command text overrules both: a name the command text mentions always counts, and --env NAME counts a name back.

The command text is the argv words of the command and the body of the stoop sh step. It is not the files the command runs. A curated name that a build script, a Makefile or a package file reads is still ignored, so a build that stamps a commit or build number into its output keeps the old stamp on a skip. Pass --env NAME to count it.

Branch names, the user who triggered a build, and the names of the machines that ran a job still count, because they can change what a command does.

A variable whose opaque value (a token, an identifier, a timestamp) is new on each of four invocations of the same key is ignored for that key from the fourth on, and only while its value is still an identifier. If it later holds a plain value, such as production, it counts again on that run and its learning is dropped, and four new identifiers can teach it again. An unset learned variable counts. Every invocation counts, skipped ones included, so a value that repeats on a run that skips still blocks learning. If a learned variable returns to one of the last sixteen distinct values it held, it counts again and is never ignored for that key again. A value older than that window cannot be recognised as a repeat. Names that look behavioural are never learned, among them SOURCE_DATE_EPOCH, IMAGE_TAG, RELEASE_SHA256, and names ending in _TAG, _SHA, _SHA1, _SHA256, _SHA512, _HASH, _CHECKSUM, _DIGEST, _EPOCH or _VERSION.

Per-job credentials issued under names the tool chooses are not curated: GitLab id_tokens, temporary AWS keys and Vault tokens. Their names say nothing about how often they change, so a step that reads one may run every time until you pass --ignore-env NAME. That costs skips, not correctness. COLUMNS and LINES are curated everywhere, so their exclusion matters only to a command whose output depends on terminal width, such as a help-text snapshot test. For such a command, pass --env COLUMNS.

The trade-off is plain. A variable that really changes what a command does, and takes a new value on every run, would be ignored. Keep such a variable in the command text or pass --env NAME. STOOP_LEARN_VOLATILE=0 and --no-learn-volatile turn learning off and keep the curated list. stoop explain names each exclusion and its reason, stoop ls lists the names each key ignores, and stoop forget --volatile KEY resets what was learned for a key.

Learned state lives in the local store beside the proofs. A CI job that does not keep its store learns nothing, but the curated list still applies. Each proof records the names it excluded. A skip needs the same excluded names as its proof, and the planner refuses a proof that excluded a learned name, because it cannot see the value that made the name excluded.

Edits while a command runs

Stoop captures a path's identity at the first observed lookup and compares recordable inputs after the command exits. A detected difference refuses the record. For a recently changed file, or one dated in the future, it also hashes the file at the content-read stop. Listed directories can be snapshotted during the run, and symbolic links are checked against their observed targets. A changed watched Git source drops blob ids from the record.

These checks sample stops, not every instant between them. A clock set back by more than two seconds can make a recent file look old. A file changed and restored within one filesystem timestamp tick may go undetected. Reads through descriptors opened before stoop started and writes through mappings or aliases the tracer cannot associate with the input are outside this check.

A path that the command both reads and writes, or a write whose destination cannot be established, may leave the run unrecorded. A file the command writes but does not read back can still be changed by another process: its output hash describes the final bytes, not who wrote them.

An editor that reads a file and writes the same bytes back through a writable file descriptor is not recorded when stoop cannot establish the last write. It runs again each time. An editor that replaces the file by a verified atomic rename can record, then skip once the input and output have converged.

Stoop does not observe individual reads and writes through a descriptor opened read-write. If another process edits the file between a write and a later read through that same descriptor, the change can go undetected.

For a nonexclusive create, another process can create the destination after stoop's entry observation but before the kernel opens it. The verified output names where the open landed, but the recorded prior can still describe the earlier absence. For path-only mutations with no returned descriptor, a link retargeted and restored between syscall entry and exit can likewise conceal where the operation landed. Avoid concurrent writers or link retargeting when a step's result depends on those races.

Read-time hashing has a 1 GiB per-run budget. Stoop reads at most one extra byte to detect overflow and refuses the record if the budget is exceeded. Directory snapshots taken during the trace are capped at 1,048,576 entries in total. Exceeding that cap also refuses the record. The directory cap applies to these snapshots, not to every later listing.

Platforms

Tracing needs Linux on x86-64 or arm64. Elsewhere stoop runs the command untraced and records nothing. Programs that use io_uring for file access are told it is unavailable (ENOSYS) so they fall back to calls the tracer can see; Node, for one, handles this.

On macOS there is one opt-in diagnostic, and it records nothing. With STOOP_DTRACE_DIAGNOSTIC=1 and passwordless sudo, stoop runs the command once under DTrace and prints what it saw: the paths it read, the lookups that failed, the paths it wrote or tried to write (a failed attempt is also listed as failed), the processes it started and the programs it ran. STOOP_DTRACE_DIAGNOSTIC=list prints each path and the tree; raw also prints every line the tracer printed. The script traces only the calls it names: open, openat, stat, lstat, fstatat, access, faccessat, getattrlist, readlink, mkdir, rmdir, unlink, rename, chdir, fchdir, the pthread chdir calls, and the creation, exec and exit of processes. Every other call is not seen, and the report does not say which. GitHub-hosted macOS runners have passwordless sudo. Cost: the spike's two-repetition trial, with an earlier script that had no return probes, measured 300 compiler invocations about 95% slower on arm64 (about 46% on Intel) and 1,000 spawns about 100% slower on arm64 (about 82% on Intel). This version has more probes, so its cost has not been measured.

On macOS stoop never skips, never writes a proof, and the planner never reads the report. Without sudo the verdict is UNKNOWN and the command runs untraced. The verdict is UNSOUND when DTrace writes anything to its error stream or reports a loss on its output, when a line cannot be read or ends before its newline, when a path does not match the length the tracer gave it (a file name with a newline, for one), when the tracer stops early or is left running, when the command's exit is not seen, when a process touches paths without a spawn edge from the command, when a path cannot be placed, and when the tracer's output cannot be read. Otherwise the verdict is no loss announced. That does not claim the report is complete: the calls the script does not trace are not seen.

On current macOS every run that starts a process is UNSOUND. The system loader opens its libraries relative to a directory descriptor in every process, and the tracer does not follow descriptors yet, so each such lookup is listed as not placed. Two more causes make a run UNSOUND. A relative path looked up in a child started by posix_spawn makes it UNSOUND, because such a child may have changed directory through a file action that no system call shows. Any call to fchdir or a pthread chdir call makes it UNSOUND, because the working directory is then unknown. A symlink's target is never seen, only the link's own name. DTrace gives no error code, so a failed lookup is listed as failed whatever the cause. A directory counts as read when it is opened, and its entries are not listed exactly. A Mac with System Integrity Protection enabled has not been tested.
