The trace

stoop starts the command under ptrace with a seccomp filter in front of it. The filter lets ordinary system calls through untouched and stops only the ones that name a file, a directory or a connection, so a traced build pays for its file activity, not for every call it makes. Children, threads and anything they exec are followed.

From those stops stoop collects every path the process tree:

  • opened for reading,
  • executed (the compiler, the interpreter, a helper script),
  • looked up, including lookups that found nothing,
  • listed as a directory,
  • followed as a symlink,

and every path it created, rewrote, renamed, removed or changed the mode of inside the repository.

The proof

For eligible input candidates, stoop compares the first observed identity with the state after exit before saving that proof. If it changed, the run is not recorded. A timestamp, xattr or bind-alias change made by the command can make stoop refuse to record. Paths affected by the command's own write footprint and other unprovable routes retain the earlier recorder behavior; the limits matter. Threads that share a working directory or descriptor table can redirect a path between stoop's look and the kernel's lookup. A raced call can be attributed to a file it did not affect, so an outside edit to that file can be recorded even if its earlier read route was observed correctly.

When the command exits 0, stoop writes a proof: a JSON file under .stoop/proofs/ holding

PartWhat is stored
InputsEach path with an id: a hash of every byte for a file, prefixed x: when any execute bit is set and f: when none is, a hash of the entry list for a listed directory, the target for a symlink, and "absent" for a path inside the repository that was looked for and not found.
EnvironmentA hash of each variable's value. See the environment below.
OutputsWhat the run left inside the repository, with hashes. A skip needs them still in place. Paths the run created and then removed again are listed as removed.
ProbesFor each --probe command, a hash of what it printed.
Directory and repositoryThe working directory relative to the root and, for an external store, a repository identity.
PlatformThe operating system, architecture, tracer and tracer version that observed the command.

Inputs and outputs inside the root are stored as relative paths, so a proof stored with the checkout can move with it. Paths outside the root stay absolute. A failing run records nothing. Neither does a run started with --no-record.

Before the run first writes a path, stoop also notes what that path held: absent, a directory, a link and its target, or a file with its content hash. A skip does not read this record.

When a plain-path content open is followed by a verified same-directory atomic replacement of a single-link regular file with one traced task alive, the proof also carries the exact prior as an input. stoop binds the prior to the earlier observation, checks the replacement source at rename entry and its landing at a successful exit, then matches that landing and source digest to the final output. A proof whose input and output differ cannot match both against one stable file. A later idempotent run can record matching input and output. If the witness cannot be verified, the earlier recorder behavior remains; see its limits.

For a regular file in a simple SHA-1 Git worktree, stoop can record a Git blob id on an input or content-prior when all conversion attributes are unspecified and core.autocrlf is unset or false. The checked attributes are text, eol, filter, ident, working-tree-encoding, export-subst and the legacy crlf. Explicitly unset attributes also omit the id. The proof retains the observed attribute and configuration state even when a conversion prevents an id. If the state is unknown or changes during the run, both the id and its basis are omitted.

Blob ids are omitted for submodule paths, SHA-256 repositories, inherited GIT_* variables other than GIT_ASKPASS, GIT_EDITOR, GIT_MERGE_AUTOEDIT, GIT_PAGER, GIT_SEQUENCE_EDITOR and GIT_TERMINAL_PROMPT, redirected Git directories or attribute sources, Git config includes, a symbolic link at the global configuration or attributes file (common with dotfile managers, and it declines every blob id in every run), and other cases where the checks cannot establish a simple worktree. Untracked files have no blob id, so the planner hashes them as it did before.

A run drops every blob id it recorded when it changes something Git reads for attributes or configuration. stoop watches a fixed set of those files: the global and system configuration and attribute files that git var -l reports, the repository's config, config.worktree, commondir, index and info/attributes, every directory and link on the way to any of them, and every file reached through a hard link to one of them. A write, rename, removal, link or owner change that names a watched file drops the run's ids. So does a change to any .gitattributes file in the repository, a link, device or FIFO node created inside the repository, a directory or link moved inside it, and a link or non-empty directory removed from it. An owner change of any path inside the repository does too, because a path's owner can decide whether Git can read its attribute files. sed -i does this when it replaces a file, so a build script that edits files in place loses its blob ids for that run. Writes to other files outside the repository, such as temporary files and tool caches, keep them. So do writes to ordinary files in the repository that have no second hard link name, and writes to the object and log areas of .git. A step that writes the index (git add, git commit, and often git status) drops them too. A Git whose git var -l does not report the global configuration and attribute sources declines every blob id. The CI runners' Git 2.56 reports them.

Outputs, kind-only priors, symlinks, directories, absent paths and paths outside the root also carry no blob id. stoop never runs clean filter drivers. It computes each eligible blob id from the same bytes as the file's BLAKE3 hash and omits the id if the read length changes. Runtime skip checks compare content ids. The planner's prefilter (stoop plan --prefilter on, the default) compares a recorded blob id with the blob at the planned revision when the proof has one, and hashes the file otherwise; see the CI reference.

Proofs are specific to their platform and tracer. A Linux x86-64 proof cannot skip a Linux arm64 command, even when they share a store or Git remote. Proofs made before the current safety format are treated as cold; run the command on a supported Linux platform to record a fresh one. New proofs use a format older stoop versions cannot read, so update runners sharing a store. stoop ls shows the recorded platforms. macOS has no tracer, so it runs commands without recording or skipping; stoop explain reports that they would run. The one macOS exception is the opt-in DTrace diagnostic, which prints a report of what a command did and records nothing.

The comparison

Next time, before running anything, stoop loads the proofs for the key, newest first, and checks each in turn: same platform and tracer, not expired, same environment, every input still the same, every output still in place, every probe still printing the same thing. The first proof that passes means a skip. If none passes, the command runs and the reason given is what differed from the newest proof. stoop explain prints what differed in each proof it checked.

Checking costs one hash of every recorded input. For the cargo build in the getting started transcript that was 668 inputs, the Rust toolchain included, in 289 ms. Every file is hashed byte for byte, with no sampling and no trust in timestamps.

Executable bits are part of a file's identity, so a proof recorded by an earlier stoop has no x: ids and a command that read an executable runs again once after upgrading. The new proof then skips as usual.

Keys

A key names one command in one place. By default it is the program's name plus a hash of the full argument list and the working directory relative to the repository root, for example cargo-46fcb2881638d3cc. The root is the nearest ancestor containing a .git directory or file. A nested repository uses the inner root; without .git, the working directory is the root. --root DIR selects a different root. Symlinked paths are resolved to their physical directories.

Proofs live under <root>/.stoop by default, so separate roots have separate stores. With an external --store or STOOP_STORE, automatic keys also include a repository identity. The configured Git origin URL identifies the repository, so checkouts with the same origin can share proofs. Local origin paths are resolved relative to the checkout. Without an origin, the physical root path is the identity: separate roots stay separate, and moving one starts with a cold cache in an external store. The URL or path is hashed before it is stored.

--key NAME keeps the chosen name, while each proof still has to match the working directory and repository identity. Proofs recorded before directory tracking are rerun once. stoop explain and stoop ls show the directory, with literal percent signs and non-UTF-8 bytes percent-escaped.

In shell mode (stoop sh, used by GitHub Actions), the key comes from the step's script contents, its arguments, the workflow name, the job name and the working directory. The script file itself is not an input: the runner gives it a new name on every run.

Branches, reverts and history

Proofs are content-addressed. They don't know which branch or commit made them, only what the command read. Each key keeps its 8 most recent proofs, so a branch that matches what main already proved can skip, and so can a revert, as long as the earlier proof's conditions still hold.

That last part matters for builds. A proof requires the outputs its run left in the repository to still be there and unchanged. If a later build rewrote target/, an earlier build proof no longer matches even after you revert the source, so the build runs again. Steps with no outputs in the repository (tests, linters, type checks, or anything writing elsewhere) do reuse earlier proofs across a revert. Restoring outputs on a skip is on the roadmap, not built.

The environment

A variable that a program reads never appears in a file trace, so the whole environment counts. Two groups are left out:

  • The runner's per-run bookkeeping: anything starting GITHUB_, RUNNER_, ACTIONS_, INPUT_ or STOOP_, unless the command text names it.
  • Values that differ on every start of the same machine: _, PWD, OLDPWD, SHLVL, TERM, HOSTNAME, INVOCATION_ID, JOURNAL_STREAM, SSH_AUTH_SOCK, XDG_RUNTIME_DIR.

--ignore-env NAME leaves out one more. --env NAME puts one back in, for example a GITHUB_ variable the step depends on without naming it.

When it runs anyway

stoop fails wide. Each of these means the command runs, and the ones marked "not recorded" also mean no proof is written:

SituationWhat happens
No proof for the keyRuns, then records.
Newest proof older than --max-age (7 days by default)Runs, then records.
STOOP_FULL=1Runs even when a proof matches, then records.
The command failedExits with its code; not recorded.
The trace may be incompleteNot recorded, with the reason.
A traced path cannot be represented as UTF-8Not recorded: the proof must name the exact path.
The command read .gitNot recorded: a skip could hide a history change. Add .git to .stoopignore if that read cannot change the result.
The command used the network or a local serviceNot recorded, naming the destination, unless a --probe covers it or --allow-network is set.
A probe failed, or changed while the command ranNot recorded.
Tracing is unavailable (including macOS)Runs untraced; never skips or records.
STOOP_OFF=1Runs the command directly; no tracing, no skipping.
