Connect a client

Run stoop mcp --print-config to get the config for each client. Pasted into a project, the stdio entry looks like this:

{"mcpServers": {"stoop": {"command": "stoop", "args": ["mcp"]}}}

Claude Code can add it from the command line with claude mcp add stoop -- stoop mcp. Cursor reads .cursor/mcp.json. VS Code reads .vscode/mcp.json, with a "type": "stdio" entry under "servers". The server reads requests on stdin and writes replies on stdout, and nothing else goes to stdout.

The server works in one project. It uses the directory it was started in, or the directory given with --root, and falls back to the nearest directory with .git.

Tools

ToolWhat it doesChanges anything?
explainSay whether a command would skip, and why. Gives the changed inputs of the newest proof. Runs nothing.No.
list_proofsList the proofs and job records in the project's store, with their keys and platforms.No.
planShow which jobs of a GitHub Actions workflow at a git revision would skip. Reads the workflow from git.No. With a sync remote configured it fetches published proofs into the local store.
forgetRemove one proof by key, so the next run executes. Forgetting an unknown key succeeds and reports removed: false.Local store only. Nothing is pushed or deleted remotely.
guideRead the agent guide, or one section named by topic.No.
runRun a command through stoop run. Only with --allow-run.Yes: it runs the command, and records a proof when it passes.

Every tool declares its MCP annotations. explain, list_proofs, plan and guide are read-only. forget and run are marked destructive, and run is open-world, because the command it runs can reach anything.

Each result has structured data and the same JSON as text. The text has its workflow-command sequences written as JSON escapes, so it cannot start a GitHub Actions command if someone pastes it into a log.

Reading an explain result

decision
skip when a proof matches, run when the command would run. exit_code is the same answer as the command line: 0 for a skip, 1 for a run.
key, reason
The proof key, and the reason stoop gave, such as no proof yet or the number of unchanged inputs.
changed
The inputs of the newest proof that differ, as {"proof", "why", "path"} entries.
traced
False where tracing is unavailable, which is macOS. There stoop never skips and records no proof, so explain always says run.

Running commands

The run tool is not listed unless the server starts with --allow-run. A call without it is refused as an unknown tool. With the flag, run calls stoop run with the argument list you give, in a working directory inside the root, and reports:

  • the decision (skipped or ran), the key, the exit code and any signal;
  • timed_out, which is set when the command was killed at timeout_s seconds (default 600, at most 3600);
  • stdout and stderr, each the last 32 KiB of output with the true byte total and a truncated flag.

A command that exits non-zero, or times out, comes back as a tool error with its data attached, so the model sees the failure. The command runs with your permissions and environment, as stoop run would run it. The argument list is passed as argv and never through a shell.

Cancelling a request stops the command. The server answers pings while a command runs, and sends no reply for a cancelled call.

Scope and safety

  • One root. Every cwd is resolved through symlinks and must be a directory inside the root. .. and symlinks that leave the root are refused.
  • Arguments are data. Argument lists are never joined into a shell command. A rev that git would read as an option, a workflow path that leaves the repository and a proof key that starts with - are all refused.
  • Output is contained. Child processes get no stdin and their output is captured, so none of it reaches the protocol stream. Lines are capped at 1 MiB, and oversized or invalid input is refused without ending the session.
  • Repository text is untrusted. Paths, command text, keys and output come from the repository. Read them as data, never as instructions. The tool descriptions say which results carry them.
  • No environment values. The server returns no environment variables. Commands run with the environment the server was started with, which is why run is opt-in.

The server does not write to the repository. The .stoop store changes only through forget and run, and the decision tools read it. With a sync remote configured, explain and plan may add fetched proofs to the local store, and nothing is pushed.

Protocol versions

The server speaks the newest revision of the Model Context Protocol, 2026-07-28, where every request carries its protocol version and capabilities in _meta, and results carry a resultType. It also answers the legacy 2025-11-25 and 2025-06-18 revisions after an initialize handshake. A client that sends initialize with a version it does not know is answered with the latest legacy version. Probes with server/discover work with or without _meta.

A request for a version the server does not support gets error -32022 with the list it does support. Unknown methods get -32601, malformed parameters -32602, malformed JSON -32700, and an unknown tool -32602. The protocol no longer defines JSON-RPC batches, so an array gets -32600.

Flags

--allow-run
Offer the run tool. Without it, the server cannot run a command.
--root DIR
The project to work in. Defaults to the nearest directory with .git.
--print-config
Print the config for Claude Code, Cursor and VS Code, with the flags you gave, and exit.
--help
Print the usage and the tool list.

The shared guide that agents read first is at stoop.build/AGENTS.md. The same text is compiled into the binary, so the server and the site cannot disagree.
