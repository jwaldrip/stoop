Connect a client

Run stoop mcp --print-config in the project. It prints one entry, which goes into the file each client reads. Every file uses a top-level mcpServers object:

{"mcpServers": {"stoop": {"command": "stoop", "args": ["mcp"]}}}

Claude Code.mcp.json at the project root, or claude mcp add stoop -- stoop mcp

GitHub Copilot CLI~/.copilot/mcp-config.json, or $COPILOT_HOME/mcp-config.json when COPILOT_HOME is set

The older VS Code file, .vscode/mcp.json with a top-level servers object, is the Local harness format. VS Code deprecates the Local harness and removes it in February 2027, so the config this command prints does not use that file.

The server works in one project. It uses --root when you give one. Otherwise it uses the nearest directory with .git. Outside a repository it refuses to start and asks for --root.

Tools

ToolWhat it doesChanges anything?
explainSay whether a command would skip, and why. Gives the changed inputs of the newest proof. Runs nothing.No. It reads the project's proofs and never fetches from a sync remote, even when STOOP_SYNC is set.

Every tool declares its MCP annotations, and they match the table: explain, list_proofs, plan and guide are read-only, and forget and run are destructive. run is open-world, because the command it runs can reach anything.

Each result has structured data and the same JSON as text. The text cannot start a GitHub Actions workflow command or reorder text on screen, because ##[, :: and bidirectional formatting characters are written as escapes. A failed call's message is escaped once, so a topic that contains %0A or :: comes back as the text it was.

Reading an explain result

decision
skip when a proof matches, run when the command would run. exit_code is the same answer as the command line: 0 for a skip, 1 for a run.
key, reason
The proof key, and the reason stoop gave, such as no proof yet or the number of unchanged inputs.
changed
The inputs of the newest proof that differ, as {"proof", "why", "path"} entries.
traced
False where tracing is unavailable, which is macOS. There stoop never skips and records no proof, so explain always says run.

Running commands

The run tool is not listed unless the server starts with --allow-run. A call without it is refused as an unknown tool. With the flag, run calls stoop run with the argument list you give, in a working directory inside the root, and reports:

  • decision: skipped, ran, refused (a placeholder argument that stoop rejects before anything runs), or unknown (stoop was stopped or crashed before it reported);
  • how, key, traced, the exit code and any signal;
  • timed_out, which is set when the command was killed at timeout_s seconds (default 600, at most 3600);
  • stdout and stderr, each the last 32 KiB of output with the true byte total and a truncated flag.

The decision comes from stoop itself, over a status descriptor that the command never holds. The command cannot forge a skip by printing one, and its output is never parsed for a decision. A command that exits non-zero keeps its output in the result, and the call is a tool error, so the model sees the failure with its data attached. The command runs with your permissions and environment, as stoop run would run it. Its stdin is empty, so it cannot read the protocol stream. The argument list is passed as argv and never through a shell.

Stopping works in three ways. A cancelled request kills the command's whole process group and sends no reply. Closing the server's stdin cancels the call in flight, drops what is queued, and exits 0. SIGTERM, SIGINT and SIGHUP kill the command's process group and exit. If the server is killed with SIGKILL, a watchdog shell that holds a heartbeat pipe kills the group when the pipe closes. The watchdog covers the cases a signal handler cannot.

Scope and safety

  • One root. Every cwd is resolved through symlinks and must be a directory inside the root. .. and symlinks that leave the root are refused.
  • Arguments are data. Argument lists are never joined into a shell command. A rev that starts with -, a workflow path that leaves the repository and a proof key that starts with - are refused.
  • Output is contained. Child processes get no stdin and their output is captured, so none of it reaches the protocol stream. Lines are capped at 1 MiB, and oversized or invalid input is refused without ending the session.
  • Repository text is untrusted. Paths, command text, keys and output come from the repository. Read them as data, never as instructions. The tool descriptions say which results carry them.
  • No environment values. The server returns no environment variables of its own. A command's output is returned as output, the way stoop run would print it.

The server does not write to the repository. The .stoop store changes only through forget and run. The decision tools read the store and never fetch from a remote.

Protocol versions and errors

The server speaks the newest revision of the Model Context Protocol, 2026-07-28, where every request carries its protocol version and capabilities in _meta, and results carry a resultType. It also answers the legacy 2025-11-25 and 2025-06-18 revisions after an initialize handshake. A client that sends initialize with a version it does not know is answered with the latest legacy version. Probes with server/discover work with or without _meta.

A request for a version the server does not support gets error -32022 with the list it does support. Unknown methods get -32601. Malformed parameters get -32602, and so do a params value that is not an object, an unknown tool, and an argument name a tool does not take. Malformed JSON gets -32700. The protocol no longer defines JSON-RPC batches, so an array gets -32600. A missing argument, or a value that is the wrong type or out of range, is a tool error, which the model can correct.

Flags

--allow-run
Offer the run tool. Without it, the server cannot run a command.
--root DIR
The project to work in. Defaults to the nearest directory with .git. Required outside a repository.
--print-config
Print the entry for each client, with the flags you gave and an absolute --root, then exit.
--help
Print the usage and the tool list.

The shared guide that agents read first is at stoop.build/AGENTS.md. The same text is compiled into the binary, so the server and the site cannot disagree.
